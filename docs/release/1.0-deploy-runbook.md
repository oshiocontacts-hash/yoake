# Yoake 1.0 デプロイ手順書

この手順は、MemberPortal、Yoake ランチャー・ゲーム、`horizon-relay` の social リスナーを本番公開するための運用台本です。コマンドは例であり、`<ここに入れる>` 形式の値は実行前に置き換えます。実際の秘密鍵、`host_token`、grant、開設券、VPS の住所は、この文書・チャット・チケット・コマンド履歴に記録しません。

> **公開の停止条件**  
> 中継の資料（`yoake-social-ops.md`、`yoake-social-transport.md`）では social transport はまだ草案で、ランチャーとゲームは social リスナーを使用していません（ランチャーの部屋タブ自体はポータルの API を呼びますが、中継への接続とエンドツーエンド暗号化は未統合という扱いです）。ポータル統合、ホスト側の接続処理、エンドツーエンド暗号化が完了するまでは、プレイヤーが参加できる稼働中のサービスとして公開してはいけません。既存の招待コード・LAN の経路とは独立しており、social が使えないときに認証なしの参加へフォールバックしてはいけません。  
> 公開承認と完了証跡：【持ち主と埋める：統合完了を確認した担当、確認日時、検証結果の記録先】

## 1. 全体の図と役割

### 構成図

```text
                         ポータル API
              ホスト / ゲストの操作に応じて利用
                                      ┌──────────────────┐
                                      │ MemberPortal     │
                                      │ ・参加可否を判定 │
                                      │ ・grant に署名   │
                                      │ ・開設券に署名   │
                                      └────────┬─────────┘
                                               │
                       session / grant / 開設券 / relay（host:port）
                                               │
                        ┌──────────────────────┴──────────────────┐
                        │ Yoake ランチャー                       │
                        │ フレンド画面の部屋タブ                  │
                        │ 一時 JSON を本人だけ読めるファイルに保存 │
                        └──────────────────────┬──────────────────┘
                                               │
                         --yoake-social-handoff <パス> のみを渡す
                                               │
                        ┌──────────────────────┴──────────────────┐
                        │ Yoake ゲーム                            │
                        │ ・handoff ファイルを読んだら削除         │
                        │ ・ホストは Provision / Retire を送信     │
                        │ ・ゲストは grant を送信                  │
                        │ ・ホストは grant と host_token で pairing│
                        └──────────────────────┬──────────────────┘
                                               │
                           TLS 1.3、中継へ直接 TCP 接続、CA をピン留め
                                               │
                                      ┌────────┴─────────┐
                                      │ horizon-relay    │
                                      │ social リスナー  │
                                      │ ・署名を検証     │
                                      │ ・部屋を管理     │
                                      │ ・pairing / 転送 │
                                      └──────────────────┘

MemberPortal ─ ─ ─ 直接通信なし ─ ─ ─ horizon-relay
```

### 各要素の役割

| 要素 | 担当すること |
| --- | --- |
| MemberPortal | 部屋の作成・一覧・参加・削除の API を提供します。フレンド、グループ所属、ブロックを確認して grant を発行し、Ed25519 鍵で grant と開設券に署名します。中継の `host:port` をゲーム側へ返します。 |
| `horizon-relay` の social リスナー | ポータル公開鍵で grant と開設券の両方を検証します。`relay_id`、`host_token`、期限、nonce、部屋数などを検査し、ホストとゲストを pairing して転送します。ポータルへのクライアント接続や、ポータル用の中継側資格情報はありません。 |
| ランチャー | フレンド画面の部屋タブを担います。受け取った値を本人だけ読める一時 JSON ファイルに保存し、ゲームへは `--yoake-social-handoff <パス>` だけを渡します。通常版はゲームのインストール・更新を担います。 |
| ゲーム | handoff ファイルを読んだら削除します。ホスト自身が中継へ Provision を送って部屋を開きます。ゲストは grant を送り、ホストは同じ grant と `host_token` で pairing します。ホストはポータル公開鍵を独立にピン留めして grant も検証します。 |

ポータルから中継への直接通信はありません。ポータルが部屋を削除しても、その通知が直接中継へ届くのではなく、中継が開設券の `session_exp` を強制します。早めに閉じる場合はホストが `ToRelay::Retire` を送ります。

### 基本シーケンス

1. ホストが `POST /api/social/v1/sessions` を呼びます。ポータルは `session_id`、`host_principal`、一度だけ返す `host_token`、署名済み `provision {ticket, signature}`、`relay`、`expires_at` を返します。ポータルが保存するのは `host_token` の SHA-256 だけです。
2. ホストのゲームが中継へ Provision（開設券と `host_token`）を送り、自分で部屋を開きます。
3. ゲストが `GET /api/social/v1/sessions` で参加できる部屋を確認します。自分の部屋は `mine: true` です。
4. ゲストが `POST /api/social/v1/sessions/:id/join` を呼びます。ポータルは参加可否を確認し、期限付き grant、署名、中継の住所を返します。
5. ゲストのゲームが中継へ grant を送ります。ホストのゲームが同じ grant と `host_token` を送ると、中継が両者を接続します。
6. 部屋を閉じる場合は、ポータルでは `DELETE /api/social/v1/sessions/:id`（正常時は 204）、中継ではホストが `retire` を送ります。
7. 中継の再起動後に同じ部屋を開き直す場合は、ホストが `POST /api/social/v1/sessions/:id/provision`（以下、「`/provision` の再実行」）で新しい開設券を受け取り、ゲームから再び Provision を送ります。ポータルが中継へ自動復旧を指示するわけではありません。

部屋の `session_exp` は発行から 12 時間以内で、延長には新しい開設券を使います。ホストごとの同時部屋数は 3 までです。

中継が検査する時間の目安は次のとおりです。いずれも時計ずれの許容幅はありません。

| 対象 | 内容 | 出典 |
| --- | --- | --- |
| grant の有効時間 | 設計の要点では 240 秒。中継は最大 300 秒先の期限まで受け付けます。transport 文書には「実際は 120 秒」とあり、資料間で食い違います。【要確認：ポータル側が実際に発行する秒数】 | spec 抜粋、transport |
| 開設券の `exp` | 現在から 300 秒以内の未来 | transport |
| 開設券の `session_exp` | 現在から 12 時間以内の未来 | transport |
| 開設券の `relay_id` | 中継の `HORIZON_RELAY_ID` と一致しなければ拒否 | spec 抜粋、transport |
| 開設券の `nonce` | 1 回しか使えない。キャッシュはメモリだけで最大 4096 件、`exp` を過ぎると捨てる。いっぱいのときは新しい部屋を拒否し、同じ部屋の再送は通る | transport |
| 終了した部屋の ID | 300 秒は予約され、再利用できない | transport |マルチプレイの利用では、利用者が選んだサービスへゲームデータが送信され得ます。Yoake ビルドが利用データやクラッシュレポートを送信することはありません。

## 2. ポータル側

MemberPortal のコードはこのリポジトリにありません。以下の空欄を実装担当と持ち主が埋めてから実行します。

### release の流れ

1. 配備対象を確定します。  
   【持ち主と埋める：MemberPortal のリポジトリ、ブランチ、コミット、バージョン、配備担当、承認者】
2. 配備方法を確定します。  
   【持ち主と埋める：ビルド手順、配備先、実行環境、設定の反映方法、データベース移行の有無と手順】
3. ステージング用の `YOAKE_SOCIAL_SIGNING_KEY`、`YOAKE_SOCIAL_RELAY`、開設券へ入れるステージング用 `relay_id` を設定します。  
   【持ち主と埋める：ステージングの設定値を保管する場所と反映コマンド。秘密鍵そのものは記入しない】
4. ステージングへ配備します。  
   【持ち主と埋める：配備コマンド、完了確認コマンド、正常終了の判定】
5. ホストの部屋作成、ゲストの一覧・参加、期限切れ・不正署名の拒否、中継再起動後の `/provision` の再実行をステージングで確認します。  
   【持ち主と埋める：テスト実施者、テスト手順書、結果の記録先】
6. 本番用の設定を投入します。ステージングと本番で `relay_id` を混ぜないことを確認します。  
   【持ち主と埋める：本番の設定反映コマンドと二重確認の担当】
7. 本番へ配備します。  
   【持ち主と埋める：配備コマンド、メンテナンス要否、実施時刻、担当】
8. ヘルスチェックと実際の API 呼び出しで、部屋作成・参加・開設券の再発行を確認します。  
   【持ち主と埋める：ヘルスチェック URL、認証を伴う確認手順、判定基準】
9. 失敗時は MemberPortal の巻き戻し手順を実行します。  
   【持ち主と埋める：前版の識別子、巻き戻しコマンド、データベース移行を戻せるか、復旧確認手順】

### `YOAKE_SOCIAL_SIGNING_KEY` と `YOAKE_SOCIAL_RELAY`

| 設定 | 入れる値 | 配備時の確認 |
| --- | --- | --- |
| `YOAKE_SOCIAL_SIGNING_KEY` | ポータルが grant と開設券へ署名する Ed25519 署名鍵 | 秘密鍵をポータル以外へ配らないこと。鍵のファイル・文字列表現、環境変数への投入方法は【持ち主と埋める：MemberPortal が要求する形式と秘密情報の投入方法】。 |
| `YOAKE_SOCIAL_RELAY` | ゲームへ返す中継の `<DNS名>:<ポート>` | クライアントから中継へ直接到達できること。TLS の DNS 名と一致させること。ステージングと本番の値を分けること。 |
| 開設券の `relay_id` | 中継の `HORIZON_RELAY_ID` と同じ識別子 | 異なる `relay_id` の券は中継が拒否すること。ポータル側の設定名・紐付け方法は【持ち主と埋める：実装に合わせた設定名と手順】。 |

### 署名鍵の作り方

採用するツール、実行場所、鍵形式：【持ち主と埋める：Ed25519 鍵を生成するツールとバージョン、実施マシン、MemberPortal へ渡す形式】

資料で確かめられる条件は次のとおりです。具体的な生成コマンドは資料にないため、持ち主が検証した手順をここへ記入します。

- ポータルの署名鍵は Ed25519 です。
- 中継の `HORIZON_RELAY_PORTAL_KEY` に入れるのは、生の 32 バイトの公開鍵を 64 桁の小文字 hex にしたものです（ファイルパスではありません）。
- 秘密鍵をポータル以外に置きません。

生成手順：【持ち主と埋める：秘密鍵の生成コマンド、公開鍵の取り出しと hex 化の手順、MemberPortal が要求する秘密鍵の形式への変換、作業用ファイルの安全な削除】

公開鍵の hex ができたら、内容を画面に出さずに形式だけを検査します（鍵ファイルの名前は例です）。

```sh
test "$(tr -d '\n' < <ポータル公開鍵hexの出力ファイル> | wc -c)" -eq 64
tr -d '\n' < <ポータル公開鍵hexの出力ファイル> | grep -Eq '^[0-9a-f]{64}$'
```

### 署名鍵の保管

| 項目 | 本番運用で確定する内容 |
| --- | --- |
| 保管場所 | 【持ち主と埋める：秘密情報管理基盤、暗号化された保管領域、オフライン保管の有無】 |
| 管理責任者 | 【持ち主と埋める：鍵の持ち主、日常の管理者、代理者】 |
| アクセス権 | 【持ち主と埋める：読み取り・投入・入れ替えを許可する役職またはアカウント、承認手順】 |
| バックアップ | 【持ち主と埋める：暗号化方式、保存場所、世代数、実施頻度、担当】 |
| 復元訓練 | 【持ち主と埋める：復元手順、最終実施日、結果の記録先】 |
| 廃棄 | 【持ち主と埋める：旧秘密鍵と一時ファイルの安全な廃棄手順】 |

中継に必要なのは公開鍵だけなので、ポータルの署名秘密鍵は中継マシンに置きません。ゲームへも公開鍵だけを配ります。

### 署名鍵の入れ替え手順と影響

中継の `HORIZON_RELAY_PORTAL_KEY` は 1 個の 32 バイト公開鍵です。複数のポータル公開鍵を同時設定する方法は資料にないため、二鍵併用による無停止切り替えを前提にしません。

1. 切り替え担当、実施時刻、参加への影響、停止方法を決めます。  
   【持ち主と埋める：メンテナンス時刻、告知方法、ポータルの発行・参加を止める手順、切り替え順の責任者】
2. 新しい Ed25519 鍵を「署名鍵の作り方」で生成し、公開鍵を検証します。
3. ステージングでポータル秘密鍵、中継公開鍵、ホスト側ゲームの公開鍵を新しい鍵へ切り替え、新旧の署名が期待どおり受付・拒否されることを確認します。
4. 本番では新規の部屋作成と参加を止めてから、ポータルの `YOAKE_SOCIAL_SIGNING_KEY` を更新します。  
   【持ち主と埋める：設定更新と反映のコマンド】
5. 各中継の `HORIZON_RELAY_PORTAL_KEY` を同じ新公開鍵へ更新して再起動します。ホスト側ゲームへの公開鍵配布も完了させます。  
   【持ち主と埋める：ゲームへの配布手順、全ホストの反映を確認する方法】
6. 新しい grant と開設券が受け付けられ、旧署名鍵による grant と開設券が拒否されることを確認します。
7. 中継再起動で消えた部屋について、ホストは `/provision` を再実行して新しい開設券で開き直します。ゲストは新しい grant を受け取ります。
8. 旧秘密鍵の無効化・廃棄と、切り替え記録を行います。  
   【持ち主と埋める：旧鍵の無効化場所、廃棄担当、完了記録先】

**影響：** 切り替え後、旧鍵で署名された grant と開設券は検証に失敗します。進行中の参加は失敗し得ます。中継を再起動すれば部屋は消え、ホストの開き直しとゲストの新規 grant が必要です。`relay_id` 自体を変更した場合も、旧 ID 向けの開設券は無効になります。

### 公開鍵を中継とゲームへ配る手順

1. ポータル署名鍵から公開鍵を導出し、64 桁の小文字 hex を検証します。秘密鍵を配布しません。
2. 中継ごとに `HORIZON_RELAY_PORTAL_KEY=<64桁の小文字hex>` を設定します。これはファイルパスではなく、環境変数へ直接入れる公開鍵です。
3. 設定を反映して中継を再起動し、起動ログと署名検証を確認します。再起動による部屋喪失を事前に告知します。
4. **ゲーム側への配布も必要です。** transport 文書によると、grant を検証するのは次の 2 か所です。
   - ホスト側ゲーム：ポータル公開鍵を grant とは独立にピン留めし、署名・セッション・ホスト・期限・nonce を確かめてからゲストを受け入れます。
   - 中継：同じ項目を独立に検査します（開設券も中継が検証します。ゲームは開設券を検証しません）。

   ゲスト側ゲームは grant を中継へ提示するだけで、検証するという記載は資料にありません。したがって公開鍵の配布先は「ホストになるゲーム」ですが、どのプレイヤーもホストになれるため、実際には全クライアントに必要になる見込みです。ゲスト専用のクライアントを作る場合を除き、ゲスト側を省く前提にしないでください。  
   【持ち主と埋める：ホスト側ゲームへの公開鍵の同梱・配布方法、設定名、更新を強制する方法。ゲームがどこから公開鍵を得るかは資料にありません】
5. TLS 用の `ca.der` とは別物として管理します。ポータル公開鍵は grant・開設券の検証用、`ca.der` は中継との TLS 接続用です。

## 3. 中継側

### CA と leaf の作成

実施場所は、本番プレイヤーデータのない管理マシンです。CA の秘密鍵はオフラインの署名環境に保管し、中継マシンには置きません。同期フォルダー（Google Drive、OneDrive、Dropbox など）は使用しません。

1. クライアントから直接到達できる中継の DNS 名を決めます。IP アドレスや末尾にドットのある名前は証明書生成に使えません。  
   【持ち主と埋める：`<dns-name>`、DNS 管理担当、正しいアドレスへの設定手順】
2. CA 用ディレクトリーを用意します。Unix では生成コマンドが不足したディレクトリーを `0700` で作成します。Windows では先にディレクトリーを作り、ACL を固定します。

   ```bat
   mkdir <dir>
   icacls <dir> /inheritance:r /grant:r "%USERNAME%:(OI)(CI)F"
   ```

3. オフライン CA 環境で、5 年有効な CA と 30 日有効な leaf を作成します。既存の出力は上書きされません。

   ```sh
   horizon-relay --gen-social-certs <dir> --host <dns-name>
   ```

4. 生成物を次のとおりに取り扱います。

   | ファイル | 内容 | 配置・保管 |
   | --- | --- | --- |
   | `ca.der` | クライアントがピン留めする CA 証明書 | クライアントへ配布し、バックアップします。 |
   | `ca-key.der` | PKCS#8 DER の CA 秘密鍵 | 暗号化したオフライン保管と署名マシンだけに置きます。中継・クライアントへは絶対に入れません。 |
   | `leaf.der` | 30 日有効な中継証明書 | 中継へ配置します。 |
   | `leaf-key.der` | PKCS#8 DER の leaf 秘密鍵 | 中継だけに配置します。 |

5. `ca.der` と `ca-key.der` のオフライン保管、バックアップ、アクセス権を確定します。  
   【持ち主と埋める：オフライン保管場所、暗号化・バックアップ方法、鍵の持ち主、復元手順】
6. `leaf.der` と `leaf-key.der` だけを scp/SSH などの安全な経路で中継へ送ります。チャットや電子メールでは送りません。

   ```sh
   scp <dir>/leaf.der <dir>/leaf-key.der <中継管理者>@<中継の管理用アドレス>:<安全な一時配置先>/
   ```

7. 中継で、証明書を `0644`、秘密鍵を通常ファイル・`0600` にし、サービスユーザーだけが読めるようにします。

   ```sh
   install -o horizon-relay -g horizon-relay -m 0644 <一時配置先>/leaf.der /var/lib/horizon-relay/leaf.der
   install -o horizon-relay -g horizon-relay -m 0600 <一時配置先>/leaf-key.der /var/lib/horizon-relay/leaf-key.der
   ```

8. 作業用 CA マシンに残した leaf 秘密鍵を削除します。`leaf-key.der.old` も有効な秘密鍵なので同様に保護・削除します。  
   【持ち主と埋める：オフライン保管への移動と、作業コピーの安全な削除手順】
9. `ca.der` をランチャー・ゲームへ配布します。複数 CA のピン留めが可能なので、計画的な CA 入れ替えでは新旧を併用できます。ただし、資料時点では本番 CA はクライアントに組み込まれていません。  
   【持ち主と埋める：`ca.der` の同梱・配布方法、対象バージョン、全クライアントへの反映確認方法】

CA は選択した DNS 名に制約され、そのサブドメインは含みません。leaf はその DNS SAN、`serverAuth`、`digitalSignature` を持ち、有効開始は発行の 1 時間前に設定されます。ホスト名を変更する場合は新しい CA とクライアント更新が必要です。

### leaf の更新

残り 7 日以下の警告が出る前に開始します。クライアントは CA をピン留めしているため、通常の leaf 更新ではクライアント変更は不要です。

1. オフライン CA 環境に `ca.der`、`ca-key.der`、現行の `leaf.der`、`leaf-key.der` を用意します。更新ツールは既存 leaf ペアも必要とします。  
   【持ち主と埋める：保護されたオフライン保管から現行ペアを安全に復元する手順】
2. leaf を更新します。Unix ではグループまたは他人が書き込める CA 用ディレクトリーは拒否されます。

   ```sh
   horizon-relay --renew-social-leaf <dir> --host <dns-name>
   ```

3. ツールが CA とホスト名を検査し、新しい 30 日ペアをクライアントと同じ方法で検証することを確認します。誤った `--host` では失敗し、ファイルは変更されません。旧ペアは `leaf.der.old`、`leaf-key.der.old` に残ります。
4. 新しい `leaf.der` と `leaf-key.der` だけを安全な経路で中継へ送り、上記の所有者・権限で配置します。
5. 中継を再起動します。証明書の reload コマンドはなく、稼働中のプロセスは古いメモリ内 TLS 設定を保持します。

   ```sh
   systemctl restart horizon-relay-social
   ```

6. journal で起動エラーと期限警告を確認し、実際に CA をピン留めした TLS 接続を行います。成功するまで以前のオフライン leaf ペアを保持します。
7. 確認後、作業用の秘密鍵と `.old` を所定の方法で処理し、次回期限を監視へ登録します。再起動で部屋が消えるため、ホストには `/provision` の再実行を案内します。

CA の残り 90 日未満で更新ツールが警告しますが、全クライアントへの配布を間に合わせるには、その警告を待たず数か月前から CA 入れ替えを開始します。CA 自体の有効期限をクライアントが警告する仕組みはありません。

### 設定

social リスナーには次の 5 設定がすべて必要です。証明書と秘密鍵の変数はファイルパス、ポータル公開鍵は hex 文字列そのものです。

| 変数名 | 値 | 必須・用途 |
| --- | --- | --- |
| `HORIZON_RELAY_SOCIAL_ADDR` | `<待受IP>:<socialポート>` | 必須。social リスナーのソケットアドレスです。 |
| `HORIZON_RELAY_SOCIAL_CERT` | `/var/lib/horizon-relay/leaf.der` | 必須。DER leaf 証明書のパスで、DER 本文ではありません。 |
| `HORIZON_RELAY_SOCIAL_CERT_KEY` | `/var/lib/horizon-relay/leaf-key.der` | 必須。PKCS#8 DER leaf 秘密鍵のパスで、鍵本文ではありません。 |
| `HORIZON_RELAY_PORTAL_KEY` | `<64桁の小文字hex>` | 必須。grant と開設券の両方を検証するポータル公開鍵です。 |
| `HORIZON_RELAY_ID` | `<この中継だけの識別子>` | 必須。開設券の `relay_id` と照合します。1～128 バイトの UTF-8 で、制御文字は使えません。 |
| `PORT` | `<招待コードリスナーのTCPポート>` | social ではなく、独立した既存の招待コード中継用です。未設定時は 7000 です。 |
| `RELAY_BIND` | `<招待コードリスナーの待受アドレス>` | social ではなく、既存の招待コード中継の待受アドレスを絞る任意設定です。その他の `RELAY_*` も招待コード中継用です。 |

1. ステージングと本番で必ず異なる `HORIZON_RELAY_ID` を使います。同じポータル公開鍵を共有する他地域の中継にも別 ID を割り当てます。
2. ポータルがホストへ返す `YOAKE_SOCIAL_RELAY` と、開設券へ入れる `relay_id` が同じ中継を指すことを確認します。
3. 設定を変更したら中継を再起動し、起動行を確認します。`HORIZON_RELAY_ID` を変更すると旧 ID 向け開設券は無効になります。
4. 設定の一部が不足・不正な場合、social リスナーだけが無効化され、プロセスが残ることがあります。「プロセスがある」だけで social の起動成功と判断しません。

### `horizon-relay-social.service`

既存の invite-only `horizon-relay.service` を変更せず、social 有効用に独立した単位を使います。両方が同じ `PORT` を使うなら、既存側を先に停止します。この例の単位は招待コードと social の両方を起動するため、停止・再起動は両方へ影響します。

1. 専用のシステムユーザーを作成します。

   ```sh
   useradd --system --home /var/lib/horizon-relay --shell /usr/sbin/nologin horizon-relay
   ```

2. バイナリと leaf ペアを所定の権限で配置します。  
   【持ち主と埋める：検証済み `horizon-relay` バイナリの取得元、バージョン、ハッシュ検証手順】
3. `/etc/systemd/system/horizon-relay-social.service` を作成します。実際の公開鍵はこの文書に写さず、配置先の unit または秘匿管理の仕組みにだけ設定します。

   ```ini
   [Unit]
   Description=Horizon invite and social relay
   After=network-online.target
   Wants=network-online.target

   [Service]
   User=horizon-relay
   Group=horizon-relay
   StateDirectory=horizon-relay
   StateDirectoryMode=0700
   ExecStart=/usr/local/bin/horizon-relay
   Environment=PORT=<招待コードリスナーのTCPポート>
   Environment=HORIZON_RELAY_SOCIAL_ADDR=<待受IP>:<socialポート>
   Environment=HORIZON_RELAY_SOCIAL_CERT=/var/lib/horizon-relay/leaf.der
   Environment=HORIZON_RELAY_SOCIAL_CERT_KEY=/var/lib/horizon-relay/leaf-key.der
   Environment=HORIZON_RELAY_PORTAL_KEY=<64桁の小文字hex>
   Environment=HORIZON_RELAY_ID=<この中継だけの識別子>
   NoNewPrivileges=yes
   ProtectSystem=strict
   ProtectHome=yes
   PrivateTmp=yes
   Restart=on-failure
   RestartSec=5

   [Install]
   WantedBy=multi-user.target
   ```

4. unit を反映して起動します。

   ```sh
   systemctl daemon-reload
   systemctl enable --now horizon-relay-social
   ```

5. 次の監視項目で、social リスナーが実際に起動したことを確認します。  
   【持ち主と埋める：unit の配備・変更管理手順、設定ファイルのバックアップ先、アクセス権】

### ファイアウォール

| 開ける通信 | 理由と条件 |
| --- | --- |
| `HORIZON_RELAY_SOCIAL_ADDR` の `<socialポート>/tcp` | ホスト・ゲストが中継へ直接 TLS 1.3 接続するために必要です。クライアントからの直接接続を許可します。平文フォールバックはありません。 |
| `PORT` の `<招待コードリスナーのTCPポート>/tcp` | この unit で既存の招待コード中継も使う場合だけ開けます。social リスナーとは独立しています。 |
| 【持ち主と埋める：管理用 SSH のポートと接続元】 | 証明書とバイナリの安全な配備用です。接続元を管理者の範囲に限定します。 |

1. social ポートはリバースプロキシーやロードバランサーを介さず、クライアントから中継へ直接到達させます。接続元制限はソケットの peer アドレスを使い、PROXY protocol は未実装です。
2. ファイアウォール製品と適用コマンドを確定します。  
   【持ち主と埋める：ファイアウォール製品、許可コマンド、設定の永続化方法、変更担当】
3. 適用例としては、次の形式を使います。

   ```sh
   <ファイアウォールの許可コマンド> <socialポート>/tcp
   <ファイアウォールの許可コマンド> <招待コードリスナーのTCPポート>/tcp
   ```

4. 外部から両ポートの到達可否を確認し、使わない招待コード側ポートは閉じます。social ポートでは、TCP 到達だけでなく CA をピン留めした TLS 接続も確認します。

### 更新と巻き戻し

#### バイナリ更新

1. 新しいバイナリの取得元、対象バージョン、検証値を記録します。  
   【持ち主と埋める：バイナリの取得元、バージョン、ハッシュまたは署名の検証手順、更新担当】
2. 現在の unit、バイナリ、証明書設定を退避します。leaf 秘密鍵を含む退避は暗号化し、アクセスを管理者だけに限定します。

   ```sh
   cp -a /etc/systemd/system/horizon-relay-social.service <設定退避先>/
   cp -a /usr/local/bin/horizon-relay <旧バイナリ退避先>
   ```

3. 新バイナリを別名で配置してから入れ替えます。

   ```sh
   install -o root -g root -m 0755 <検証済み新バイナリ> /usr/local/bin/horizon-relay.new
   mv /usr/local/bin/horizon-relay.new /usr/local/bin/horizon-relay
   ```

4. unit も変更した場合は `systemctl daemon-reload` を実行し、中継を再起動します。

   ```sh
   systemctl restart horizon-relay-social
   ```

5. プロセス、起動ログ、social ポート、CA をピン留めした TLS 接続、部屋の作成と参加を確認します。
6. 失敗したら、退避した旧バイナリを別名で配置して入れ替え、必要な場合だけ unit も復元します。

   ```sh
   install -o root -g root -m 0755 <旧バイナリ退避先> /usr/local/bin/horizon-relay.rollback
   mv /usr/local/bin/horizon-relay.rollback /usr/local/bin/horizon-relay
   cp -a <退避したunit> /etc/systemd/system/horizon-relay-social.service
   systemctl daemon-reload
   systemctl restart horizon-relay-social
   ```

7. 巻き戻し後も同じ起動・接続確認を行います。漏えいした鍵や CA へは、通常の巻き戻しとして戻しません。  
   【持ち主と埋める：更新・巻き戻しの判定者、実施記録先、旧版の保持期間】

#### 再起動が及ぼす影響と復旧

1. 更新、証明書入れ替え、設定変更、巻き戻しに伴う再起動では、中継上の部屋は消えます。自動復旧を前提にせず、メンテナンスとして告知します。
2. ホストは `/provision` を再実行して新しい開設券を受け取り、ゲームから Provision を送って開き直します。ゲストは新しい grant を受け取って参加し直します。
3. grant と開設券の nonce / replay キャッシュはメモリ上だけです。ホストと中継の双方で再起動により消えます。中継では、まだ有効な開設券（`exp` は最大 300 秒先）が再起動後に再利用できてしまいますが、開設券だけでは `host_token` がなければ部屋を開けません。
4. 本番統合では、再起動後に旧セッションと grant を無効化するか、永続的な replay 対策を用意します。  
   【持ち主と埋める：ポータル側の無効化手順または永続化の実装、検証手順、完了承認】
5. 認証に失敗した場合や中継が使えない場合に、認証なしの直接参加へ切り替えてはいけません。

### 監視

| 監視対象 | 見るもの・判定 |
| --- | --- |
| プロセスと再起動 | `systemctl status horizon-relay-social`、予期しない再起動、リスナー起動失敗を確認します。 |
| 起動ログ | 正常時の `horizon-relay social listener on <address>` を確認します。`horizon-relay: social listener disabled: <理由>` と `horizon-relay: can't start social listener on <address>: <理由>` を監視します。 |
| ポートと実接続 | social ポートへの直接 TCP 到達と、CA をピン留めした TLS 1.3 handshake の成功を確認します。 |
| 証明書 | leaf の残り 7 日以下の警告、有効期間外のメッセージ、CA の残存期間を確認します。期限切れ後は新しい handshake が拒否されます。 |
| 接続・リソース | 接続制限エラー、スレッド数、ファイルディスクリプター、メモリー使用量を確認します。 |
| 部屋数 | 実装上の social 部屋上限は 1024、ホストごとの同時上限は 3 です。終了済み ID の予約を含む上限は部屋上限の 4 倍です。上限接近を判定する閾値と部屋数の取得方法は【持ち主と埋める：監視方法、警告・緊急閾値】。 |
| 接続数の上限 | handshake / 最初のメッセージ待ちは全体 256、IPv4 アドレスまたは IPv6 `/64` ごとに 4、IPv4 `/24` または IPv6 `/48` ごとに 32、live connection thread は 2048 です。 |
| 時計 | ポータル・中継・ゲームの時計同期を監視します。grant と開設券の有効期限に時計ずれの許容幅はありません。 |
| エンドツーエンド動作 | 部屋作成、grant による参加、pairing、転送、retire、期限切れを定期的に確認します。 |

確認コマンドの例です。

```sh
systemctl status horizon-relay-social
journalctl -u horizon-relay-social --since <確認開始時刻>
ss -ltnp | grep -E '<socialポート>|<招待コードリスナーのTCPポート>'
```

既存の招待コード中継が 5 分ごとに出力する数は、social handshake の正常性を示しません。journal と実接続の監視が必要です。警告閾値、通知先、当番、エスカレーション先は【持ち主と埋める：監視設定、通知チャンネル、一次・二次対応者】とします。

## 5. 事故のときの手順

### 共通の初動

1. 事故責任者と記録担当を任命します。  
   【持ち主と埋める：事故責任者、連絡先、セキュリティ担当、ポータル・中継・クライアントの各担当】
2. 発見時刻、影響範囲、直近の鍵・証明書・バイナリ変更を記録します。秘密鍵、`host_token`、grant、開設券そのものを証跡へ貼らず、安全に保全します。
3. 悪用継続の恐れがある場合は、ポータルの部屋作成・参加と social リスナーを停止します。  
   【持ち主と埋める：ポータル側の停止コマンド、social だけを停止する手順、停止の承認者】  
   `systemctl stop horizon-relay-social` は、この例の unit が担う招待コード中継も止めることに注意します。
4. 利用者への告知と、認証なし参加へのフォールバック禁止を徹底します。  
   【持ち主と埋める：告知文の承認者、告知先、プレイヤー向け案内】

### ポータル署名鍵の漏えい

1. ポータルでの新しい grant・開設券の発行を止め、social 参加を停止します。漏えい鍵では攻撃者が新しい署名を作れるため、既存 grant の期限だけに頼りません。
2. 新しい Ed25519 鍵を安全な環境で生成し、旧鍵とは別の場所に保管します。
3. 新公開鍵を各中継の `HORIZON_RELAY_PORTAL_KEY` と、少なくとも全ホスト側ゲームへ配布します。配布方法は「公開鍵を中継とゲームへ配る手順」に従います。
4. ポータルの `YOAKE_SOCIAL_SIGNING_KEY` を新秘密鍵へ切り替え、旧公開鍵を検証に使わないことを確認してから中継を再起動します。
5. 旧セッション・旧 grant をポータル側で無効化します。中継とホストの nonce キャッシュは再起動で消えるため、キャッシュの喪失を失効対策として扱いません。  
   【持ち主と埋める：無効化コマンド、対象範囲、実施担当】
6. 旧鍵による grant・開設券が中継とホストの双方で拒否され、新鍵では正常に部屋作成・参加できることを確認します。
7. ホストは `/provision` で部屋を開き直し、ゲストは新しい grant で参加し直します。旧秘密鍵を無効化・廃棄し、異常な署名利用や接続がなかったかログを調査します。
8. TLS の CA はポータル署名鍵とは別ですが、他の資格情報も漏えいしていないか個別に調査します。

### CA または leaf の漏えい

#### CA 秘密鍵 `ca-key.der` の漏えい

1. social リスナーを停止し、その CA を compromised として扱います。
2. 別ディレクトリーで新しい CA と leaf を生成します。
3. 新しい `ca.der` を全クライアントへ配布し、漏えいした CA を通常の計画的入れ替えの overlap 期間に残さず、できるだけ早く全クライアントの信頼対象から削除します。
4. 一緒に暴露した可能性のある leaf 秘密鍵もすべて入れ替え、中継へ新しい leaf ペアを配置して再起動します。
5. CA をピン留めした実接続、旧 CA を信頼しないこと、部屋作成・参加を確認し、予期しない TLS 利用がなかったかログを調査します。
6. ポータル署名鍵は別の鍵ですが、そちらも含めて他の資格情報を個別に調査します。

#### leaf 秘密鍵 `leaf-key.der` の漏えい

1. クライアントは失効リストを確認しないため、漏えいした leaf では最長でその期限まで中継をなりすませる可能性があります。`leaf-key.der.old` も対応する leaf の期限までは同じ秘密情報として扱います。
2. social リスナーを停止し、緊急に CA を入れ替えるか、最大 30 日の暴露を受け入れるかを事故責任者が決定します。  
   【持ち主と埋める：採用する対応、判断者、公開再開条件】  
   CA を入れ替える場合は、上の CA 漏えい手順で新 CA の配布と旧 CA の削除を行います。
3. 新しい leaf ペアを配置して中継を再起動し、漏えいした現行・`.old` の秘密鍵を安全に廃棄します。旧 leaf を信頼する構成へ巻き戻さないようにします。
4. pinned-CA TLS 接続と social 参加を確認し、異常な TLS 利用をログで調査します。

### 中継の停止

1. `systemctl status` と journal で、プロセス停止、再起動の繰り返し、social 設定エラー、バインド失敗を切り分けます。
2. social ポートへの直接 TCP 到達、ファイアウォール、TLS 証明書と秘密鍵の一致・有効期限、システム時計、スレッド・ファイルディスクリプター・メモリー、接続・部屋数の上限を確認します。
3. 直前の更新が原因なら「更新と巻き戻し」の旧バイナリ・旧設定への復旧を行います。漏えいした鍵や証明書へは戻しません。
4. 設定と証明書が正常なら中継を再起動し、`horizon-relay social listener on <address>`、pinned-CA handshake、部屋作成・参加を確認します。
5. 再起動で部屋が消えたため、ホストは `/provision` を再実行して開き直し、ゲストは新しい grant で参加し直します。旧セッション・grant の無効化または永続的 replay 対策が有効であることも確認します。
6. 復旧できない間は social 参加を停止したままにし、認証なし参加へ切り替えません。  
   【持ち主と埋める：復旧不能時の代替運用、利用者への再告知、復旧承認者】
