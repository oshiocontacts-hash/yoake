# FR-F3-11: data-defined custom portals

## Design

### Data and layering

A portal type is `data/<namespace>/horizon/portal/<path>.json`, matching the existing content-mod data
folders. Content-mod files are read from the prepared resource root. Enabled data-pack files are layered over
them in pack order; the last file for an id wins. A bad file warns and skips only that type. `/reload` rebuilds
the registry.

```json
{
  "frame": "#example:portal_frames",
  "ignite": {
    "item": "minecraft:flint_and_steel",
    "fluid": "minecraft:lava",
    "fire": true
  },
  "size": { "min_width": 2, "max_width": 21, "min_height": 3, "max_height": 21 },
  "target": "example:moon",
  "scale": 8.0,
  "portal_block": "example:moon_portal",
  "look": {
    "tint": "#80c0ff",
    "ambient_sound": "minecraft:block.portal.ambient",
    "travel_sound": "minecraft:block.portal.trigger",
    "particle": "minecraft:portal"
  }
}
```

`frame` is a block id or a block tag. `portal_block` defaults to `minecraft:nether_portal`; a mod block using
that template has the required axis property and portal collision behavior. Size defaults to vanilla's 2x3 to
21x21, with positive finite limits and `min <= max`. `scale` is finite and greater than zero: travelling from
the source to `target` divides X/Z by it, and returning multiplies X/Z by it. At least one ignition method is
required. Item ignition uses the item's normal consumption/durability path: flint-and-steel-like items take one
damage, while fire-charge-like items are consumed. Fluid ignition accepts the placed fluid id. `fire` controls
whether placed fire lights the frame.

`look` is optional data. Ambient sound uses the existing level-event path. Tint, travel sound and particle are
parsed for the follow-up presentation work; portal rendering files are reserved for other work in this item.

The loader checks the target against the world's level registry and checks block ids against the block
registry. An unknown target warns clearly and skips the type. Frame tags resolve through the world's layered
block-tag table, so both content-mod and data-pack tags work; a missing or empty tag skips the type.

### Shared frame code

`horizon-world::level::portal` keeps the vanilla entry points unchanged and adds parameterized entry points.
The shape search receives the frame matcher, accepted fill block, and size limits. Vanilla still supplies its
obsidian tag, nether portal block, dimensions, and dimension restrictions. Custom fire and neighbour updates
call the same search and fill routines with their own parameters. A fill block copied from the nether portal
template uses the same axis state and the same update-shape removal rule when its frame is broken.

### Ignition

Before ordinary fire placement, item use asks the custom registry for a frame at the clicked face's adjacent
position. A matching item lights an empty frame and then follows the ordinary item wear/consumption code.
Ordinary nether ignition remains first and unchanged. Bucket placement asks the same registry after the fluid
is placed; a successful ignition replaces the fluid as part of filling the frame. Fire placed by other routes
uses `BaseFireBlock.onPlace`'s shared hook, with custom types checked after the vanilla nether attempt.

### Travel and return links

A custom fill block enters the existing `PortalState`, `Plan`, entity sweep, cooldown, vehicle, projectile,
arrival, and server-trip paths. `Plan` gains a custom travel descriptor containing a runtime type slot, source
level, target level and scale. The destination search accepts only the same type's fill block; the vanilla
search remains unchanged. If no exit exists, the vanilla position search runs first and its temporary frame is
replaced by the configured frame, fill and minimum dimensions before level events are flushed.

A target-side portal needs to know where “back” is when several source levels use the same type. The server
therefore records a link `(level, portal block position) -> (type, other level)` whenever an exit is found or
built, for both ends. Entering a linked portal in its target uses the recorded source; entering an unlinked
portal outside its target uses the JSON target. An unlinked portal manually built in the target cannot invent
a return level and does not transport. Links are saved in the existing `horizon_portal_arrivals.dat`; a world
without custom portals writes the same data as before. Breaking a frame removes the fill through the shared
shape update. Stale link records are harmless while no matching fill exists; compacting them is follow-up work.

The existing native portal-create, entity-portal, player-portal permission, and changed-dimension hooks cover
custom portals too. A separate WASM custom-placement/arrival callback is not added. Doing so would require a
new event record with string level/type ids, generated adapters, hook ids, and catalog/ABI updates; changing a
closed WIT dimension enum is neither needed nor permitted.

### Verification

No-resource unit tests cover JSON defaults and validation, unknown-level skipping, shape detection with custom
blocks and limits, ignition selection, and outbound/return scaling. Existing nether portal tests remain
unchanged. `tools/levels_e2e.py` has a real pack-defined fire-lit portal round trip and frame-break check.

## Implementation

- Added the `horizon/portal` JSON kind to data-pack collection and content-mod acceptance. Content mods can use
  a block copied from the `minecraft:nether_portal` template as their custom fill.
- Added validated portal definitions, defaults, look data, world-layered frame-tag resolution, and clear
  per-type warnings. Invalid sizes, scales, ignition declarations, targets, blocks and fill-axis properties skip
  only the affected type.
- Generalized the vanilla `PortalShape` scanner without changing its vanilla parameters. Added custom filling,
  item/fluid/fire ignition, axis handling and neighbour-driven fill removal.
- Extended the existing player/entity travel plan, search, creation, arrival and cooldown paths. Outbound X/Z
  coordinates divide by `scale`; linked return travel multiplies by it. Exit links cover every fill cell and
  persist with pending portal arrivals.
- Kept vanilla nether definitions and entry points separate. With no custom definitions, the vanilla scanner,
  search, creation, ignition and saved arrival fields remain in use.
- Reused existing native portal/permission/dimension hooks. No WIT, catalog, ABI or generated file changed.

## Remaining work

- `look.tint`, `look.travel_sound` and `look.particle` are validated and retained but do not yet alter rendering
  or travel feedback. `ambient_sound` is emitted on ignition, not as a continuing portal ambience loop.
- Broken-portal link records are compacted only by a follow-up; stale records do not transport while no matching
  custom frame/fill exists. Persisted runtime slots assume the same valid portal set when a pending arrival is
  loaded; changing portal definitions during `/reload` needs id-based migration.
- No dedicated WASM custom-placement/arrival event was added. It would need new string-id event records, hook
  ids, generated adapters and catalog/ABI updates; existing native hooks receive custom portal activity.
