## What was done

### Clock

* Added `ClockBank` and pure level-environment swap helpers in `crates/horizon-client/src/level_state.rs`.
* A non-vanilla level follows its dimension type's `default_clock`. Levels naming the same clock share one value; different clocks advance independently, once per server tick. Game time remains one server-wide counter and is still copied across level swaps.
* A type without a default clock keeps its own fixed day time. The pre-26 `fixed_time` tick count is now retained by `DimensionType`; it is not advanced and is sent with rate zero.
* Named clocks are read from and written to the existing `data/minecraft/world_clocks.dat`. The Overworld value keeps its existing field and write path.
* Data-pack `minecraft:world_clock` entries now participate in the existing synchronized-registry path, so a declared custom clock has a network id.
* `/time` reads and changes the source level's default clock (or an explicitly named, registered clock). Vanilla command behavior, including the Nether's no-default-clock error, is retained.
* The vanilla Overworld, Nether and End deliberately retain the port's previous shared Overworld day time, even though the 26.3 End type names another clock. This is required by the task's vanilla-compatibility rule.

### Weather

* Non-vanilla levels whose `LevelFacts.weather` allows precipitation keep independent rain/thunder flags, timers and fade levels. Their weather ticks with their level, not with another level's first pass.
* Custom weather is stored in the level's own `dimensions/<ns>/<path>/data/minecraft/weather.dat`, using the existing weather saved-data schema.
* Full level-entry synchronization sends the level's weather; entering a clear custom level explicitly clears weather retained from the previous level.
* `/weather` continues to run in the command source's level through `enter_command_level`, so it now changes that custom level's weather.
* The three vanilla levels retain the old shared weather and first-pass tick path.

### World border

* `Parked` now carries a `WorldBorder`, swapped with the rest of the level. Every custom level has independent centre, current/target size, lerp, damage, safe zone and warning settings.
* Custom borders round-trip through the level's own `data/minecraft/world_border.dat` using the existing `WorldBorder::pack/unpack` representation.
* Border changes use per-level `Sent` baselines and are broadcast only to players in that custom level. A vanilla-only server uses the old global broadcast path unchanged; with custom levels present, the shared vanilla border reaches only the vanilla levels.
* The existing native/WASM `world_border` and `set_world_border` calls accept every registered level and open an unloaded custom level temporarily when necessary. No ABI definition was changed.
* `/worldborder` already executes in the source level and therefore uses the correct custom or shared vanilla border.
* The port does **not** currently scale the Overworld border for the Nether: `border_bounds` returns the shared border unchanged and the save loader reads the Overworld file. The implementation preserves that behavior rather than introducing scaling.

### Vanilla compatibility measures

* All custom behavior is keyed on levels after the three vanilla ids. Vanilla swaps continue to copy the same shared day time, weather and border values.
* No custom weather or border file is written for a vanilla level. No new file is added to a vanilla-only save.
* Vanilla full time packets, incremental clock updates, weather events and border broadcasts retain their old branches and values.
* A save test reads `world_clocks.dat` bytes before and after a second vanilla write and asserts they are identical.

## Sandboxed mod API gaps (not added)

Services 227-235 provide level lifecycle operations, and services 108/109 already expose centre/size/lerp border operations. The catalog and generated WIT/adapters were deliberately left untouched. A complete per-level API would additionally need:

* Typed clock read/set/add/query calls taking both level id and clock id, with explicit fixed-time behavior and game-time kept separate. The existing `world-control(set-time)` drops its `dimension` field when it builds `time set ...`, so it is not a per-level operation.
* Weather read/set calls covering clear/rain/thunder flags and all three timers; a capability checked like `world-control`.
* Border read/write fields for damage per block, safe zone, warning distance and warning time, which the current border record and setter do not expose.
* A way for a mod to declare a new `minecraft:world_clock` before clients join, including registry data and reconnect semantics. Runtime-created levels can currently use clocks already in the synchronized registry (including vanilla clocks); an undeclared runtime-only clock has no packet id.

## Unverified vanilla 26.3 points

No vanilla source or prepared vanilla resources were available for verification. These points are based only on the ported code named above:

* Whether vanilla shares clocks exactly as this port did for its three levels, and how its `default_clock`, timelines and legacy `fixed_time` interact. The task explicitly requires preserving the port's vanilla behavior.
* Exact per-clock pause/rate semantics. This implementation uses the port's existing clock rate/pause state for all named clocks.
* Exact rules for which custom dimension types may have weather and what `/weather` does in a type that cannot have it. The implementation uses the existing `LevelFacts.weather` predicate.
* Exact custom-level weather/border saved-data discovery and migration behavior. The files reuse the port's existing 26.3 schemas, but vanilla was not opened to confirm them.
* Whether vanilla scales the Nether border. No such scaling exists in this port, so none was added.
* Exact full-sync and incremental packet ordering for custom clear weather, fixed time and independent borders. The implementation follows the existing packet types and level-entry order, not a vanilla transcript.
* Data-pack `world_clock` JSON contents, merge semantics and runtime registration behavior. The implementation enables the existing registry loader for that registry but does not invent a runtime registration protocol.
* Byte-for-byte vanilla saves, packets and tick results are intended by the compatibility branches and targeted test, but are not proven until the build, existing suites and e2e run.
