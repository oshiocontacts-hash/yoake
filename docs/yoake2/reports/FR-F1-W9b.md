## A finding first: the wave-2 overlay verify did not stamp horizon-client-lib and horizon-client

On Windows cargo hands rustc long command lines as an **`@argfile`** (one argument per line). The wrapper only looked at direct arguments, so for the two big
crates it saw no `--crate-name` and passed them through **unstamped**; only horizon-world (short command line) was stamped. Consequences:
* `apply --verify --overlay` in wave 2 reported "clean" for lib and client, but the compiler had been run on the **unstamped** sources for those two (the ledger and the overlay copies were produced correctly, the compile did not use them). The wave-1 verify (in-place stamps) did compile lib and client stamped, so the stamped code of the three crates was compiled once, but not the wave-2 changes (`private_types`, destructuring) for lib and client.
* Fix (`overlay.rs`): `expand_argfiles` (tested) and rustc gets an argfile of its own when the new command line is long. Debug aid: `YOAKE_STAMP_DEBUG=1`.
* With the fix the first **real** stamped build of lib and client compiled clean (apart from one W9b bridge detail, fixed below). So the wave-2 stamps are now verified for all three crates: `cargo check` through the wrapper, 8,168-ish hooks, zero errors.
Please treat the wave-2 claim "lib and client clean through the overlay" as superseded by this wave's run.

## 1 and 2. Bridges in the stamped build

Files: `crates/yoake-hook-codemod/src/overlay_bridge.rs` (new), `overlay.rs`, `bridge.rs`, `types.rs`, `crates/horizon-client/src/yoake2_mods.rs`, Cargo features, `hook-ledger/stamp-config.txt` (`bridges=true`).

After the stamping of a crate (`stamp-config` flag `bridges=true`), the overlay, never the tree:
1. copies the committed table glue of each module (`<src>/yoake_glue/tables/<crate>/<module>.rs`) into the overlay and `include!`s it into **that module**;
2. runs `bridge --nary --shallow` for **every file module**, so every module gets its own `hook_bridge_<module>.rs`, `include!`d into itself (a type private to that module is nameable there: the W4 private-type stamps are bridged; a type private to **another** module is refused with a reason, as before);
3. appends to every module a chain `__yoake_bridge_install` / `__yoake_bridge_mode` that calls its own bridge and its children's (a private child module is nameable from its parent); modules with no bridge anywhere below are left out; the crate root exports `__yoake_install_bridges(registered)` and `__yoake_bridge_mode(id)`;
4. the loader (`yoake2_mods.rs`) calls the three roots (horizon-world, horizon-client-lib, horizon-client) through `STAMPED_BRIDGES`, which exists only under `--cfg yoake_stamped` (the wrapper passes it; `workspace.lints.rust.unexpected_cfgs` declares it). In an unstamped build the list is empty and nothing changes.
Modules that already carry a committed bridge (`entities`, `game::item_use`, `mobs`, `motion`) keep it and are not generated twice. `yoake2-slice` is now a feature of horizon-world too (optional `yoake-slice` dependency, enabled through `horizon-client-lib/yoake2-slice`).

## 3. Field tables ("all fields")

`yoake-bindgen --config bindgen.json --tables <crate> --tables-dir <dir>` classifies every file module of a crate with the existing analyzer (private fields included, frozen files respected)
and writes `pub mod yoake_glue_tables { pub static FIELDS_<type>: FieldTable<T>; pub static REF_FIELDS_<type>: RefFieldTable<T>; }` for each module with a struct that has scalar fields: getters only, no setters, no bindings.
Run once over the rustdoc JSON of six crates (about 6 GB of target-doc, 4 + 6 + 1 minutes; JSON deleted). Committed:
`crates/horizon-client/src/yoake_glue/tables/{horizon_client_lib,horizon_client}/` (188 + 177 files) and `crates/horizon-world/src/yoake_glue/tables/horizon_world/` (141 files): **2.7 MB, 1,095 field-table pairs** (the spike counted 637 + 225 receiver types without a table; tables exist now for every struct with a scalar field, including ones no hook uses).
They are not referenced from the committed sources (only the overlay includes them), so plain builds are unchanged. Regenerate with the three commands above after the six `cargo rustdoc` runs of `crates/yoake-bindgen/regen.sh`.
Setters stay opt-in (`writable` in `bindgen.json`); a table gives a guest `get` on a hook argument, not `engine_call` bindings.

## 4. `&Game` read root

* Runtime (`yoake-slice`): trait `PathRootRef` (the read-only twin of `PathRoot`), `ArgSet::root_shared`, `ArgView::root_shared`, `open_path` over a shared root, `with_arg_shared::<T>` (reads `&mut` and `&` arguments and path handles of mutable and shared roots; `with_arg` on a shared-root path is `ReadOnly`). Unit test: open paths from a shared root, read two objects, refusals (`ReadOnly`, `WrongType`, `Stale`), no leftover handles.
* Generator (`yoake-bindgen`): next to `impl PathRoot for Game` it emits `impl PathRootRef for Game` (`iter()` where the mutable one has `iter_mut()`); field getters and `&self` method bindings now take `&T` and dispatch through `with_arg_shared`, so the same binding works on a `&Game` path handle and on a normal one. Glue regenerated (`game_items.rs` +70 lines; the others only change `&mut recv` to `&recv` on read-only bindings).
* Bridge: `&Game` is registered with `.root_shared(p)`: 539 hooks in the stamped build.
* **Not done:** (a) the paths a guest can open are the nine existing ones (dropped items, armor stands, orbs, paintings, item frames, cushions, experience, mobs, the local player); `Game.world` (levels) and `Game.options` (settings) have **no path and no bindings** yet: they need a `bindgen.json` target for the module that defines `World` (crate `horizon_client_render`, not in this run's rustdoc set) and for `Options`; the field tables exist, the engine_call getters do not. (b) No end-to-end wasm guest test through a generated `&Game` bridge (the loader path needs the full stamped build; unit test and `cargo check` only).

## 5. miri

`cargo +nightly miri test -p yoake-slice --lib activation` with `-Zmiri-strict-provenance -Zmiri-ignore-leaks`, Stacked Borrows and Tree Borrows: **26 passed, 0 failed, no undefined behaviour reported** (includes the W8 n-ary tests and the W9b shared-root test; both borrow models). Without `-Zmiri-ignore-leaks` the only error is the end-of-run leak check on the existing test `forgetting_cannot_keep_an_activation_alive`, which `mem::forget`s a box on purpose. Running the whole `--lib` suite under miri hangs in `codec::tests::a_huge_length_does_not_reserve` (it allocates what miri then interprets), so the filter is `activation`. The unsafe parts that miri does **not** reach: the wasm runtime and the generated glue.
