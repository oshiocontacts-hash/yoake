# FR-REM17b: client WebAssembly services `attachment-get` and `mod-call` (part a only)

Branch `yoake-free/rem17b-client`, worktree `horizon-rem17b`, from `yoake-free/merge` 0401a6a88.

## 1. What was done

### (a) `attachment-get` on the client: done

- Catalog (`crates/horizon-mod-api-gen/abi-subset-client.json`): row `client_attachment_get`, id 297, capability
  `world-storage` (the same capability as the server `attachment_get`). Signature `(holder, id, kind) -> result<option<list<u8>>, string>`.
  Interface version of the client catalog bumped `1.8.0` -> `1.9.0` (additive).
  - The name is prefixed `client_` because service names are unique across all catalogs (the server already has `attachment_get`).
  - Id 297 is the first free id after the highest used one (296). Ids 292/293 are taken by server rows.
- WIT: `crates/yoake-wasm/wit/yoake-full.wit` regenerated by `YOAKE_UPDATE_WIT=1 cargo test -p horizon-mod-api-gen --lib`
  (one new line in `client-services`). No other generated file changed content.
- Host trait macro (hand-written): `crates/yoake-wasm/src/client_services.rs` (one line).
- Host implementation: `crates/horizon-client/src/wasm_mods/client_services.rs`, `client_attachment_get`.
  It validates the id (`owner:name`, at most 128 bytes), parses the holder with the server's parser
  (`server_services::attachment_holder`, now `pub(super)`), reads the holder's map through the game's `Host::attachments`
  (the same map the server sync fills on a client) and returns the synced bytes (`server_services::attachment_bytes`, now `pub(super)`).
- Core helper: `crates/horizon-world/src/attachments.rs`: `Attachments::read_named(namespace, name)` (read-only, no registry needed);
  `read_dynamic` now calls the shared `read_key`.
- SDK helper: `crates/yoake-wasm-sdk/src/full.rs`, `client::attachment_get(holder, id, kind)`.
- Tests: `horizon-world` unit test `client_reads_a_synced_value_by_its_id_without_the_definition` (sync a server value, read it back
  by id on a client copy, unknown name gives `None`).

### (b) `mod-call` on the client: NOT done

Not started as a service. A client `mod-call` needs more than a catalog row:
- The `client-full` world has no `handle-call` export (only `server-full` has one, generated in `horizon-mod-api-gen/src/abi/wit_full.rs`).
  Adding it changes what client guests must export.
- The SDK macro that generates `handle_call` (`horizon-mod-api-gen/src/abi/sdk_full.rs`) is written for the server only.
- The host needs a client-module `handle_call` path with the same re-entrancy guard, depth counter and 1 MiB limits as
  `server_services::call_mod`, on the client module instances (which run on the client hooks thread).
So no row was added for it (an earlier draft row was removed, so nothing half-done ships).

## 3. Open points / decisions for the owner

1. A client mod can read any synced attachment id (`owner:name`) on a holder it can see. The server only lets a package read
   attachments it defined itself. The client has no definitions, so no per-package check is possible. Decide whether to
   restrict reads to the caller's own namespace (`owner == caller package id`) or keep "any synced value".
2. `Host::attachments` on a client (non-authoritative) path uses `entry().or_default()`, so reading a holder with no
   synced data creates an empty map for it. It is removed with the holder by the existing `retain`/`remove` code, but a
   read-only path that writes is not ideal; a read-only accessor on `Host` would be cleaner.
3. Client `mod-call` (part b) is left, see section 1.
4. Not run in a live game: a client mod reading a real synced attachment (player/entity/block-entity/chunk/level) end to end.
