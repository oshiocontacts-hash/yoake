# MX3K1: first real Rust guest SDK, hook multiplexing, server tick wired

Branch `yoake2/slice` on top of 84ea7d7bb (MX3R1), working tree. No git writes, no installs, no game launch. Everything is behind `yoake2-slice` or in `yoake-slice` / `yoake-bindgen` / the new `yoake-guest-sdk`; feature-off builds are unchanged. ABI notes: `docs/yoake2/ENGINE_CALL_ABI.md` (new sections: hook multiplexing, the Rust guest SDK).

## 1. Small fixes

- **`Accessor::Index` removed.** A list position silently names another element after a removal; the only way into a list is `Id`. Documented on the enum.
- **No table scan on the hot path.** Each activation record counts the path handles it opened (`paths_opened`). `Guard::close` scans `PATHS` only when the count is above 0, and `open_path` checks the 256 bound on the record, not by scanning the table. Test: a nested activation that opened no path ends without touching the outer one's handles.
- **Ticket ids saturate.** `MAX_TICKET_ID = i32::MAX - 256`; at that id the host answers `TICKET_LIMIT` instead of wrapping (so `-(256 + id)` always fits an `i32`). Unit test on the constant and `ticket_of`.

## 2. Hook multiplexing

Design (the simplest that scales to thousands of ids): **one** guest entry `yoake_hook(hook_id: i32, handle: i64) -> i64` (the guest `match`es on the id), an optional `yoake_init()` that calls the host import `hook_register(id, priority)` for every id it wants, and host-side dispatch by id.

- Host: `Host.registered: HashMap<id, priority>`, `Host.multi`. The shims call `dispatch_id(hook_id, ..)` / `dispatch_root_id(hook_id, ..)`; the old `dispatch`/`dispatch_root` are hook id 0 and a guest without `yoake_hook` is the slice's single-export guest, so every earlier test is unchanged.
- **An unregistered hook costs one hash lookup**: checked before the context is published, no activation is opened, the guest is not entered, the original runs. `runtime::stats().registered` lists `(id, priority)`.
- Ids: S2 slot ids are the small numbers; engine-synthetic hooks start at `SYNTHETIC_HOOK_BASE = 0x8000_0000`; `HOOK_SERVER_TICK = 0x8000_0001`.
- Tests with a real guest: hook 1 and hook 2 registered (with priorities 0 and 5, read back); a guest that registers only hook 1 is never entered for hook 2 or for an id nobody registered.

## 3. The Rust guest SDK (`crates/yoake-guest-sdk`)

**A core module is produced without installing anything.** With only `wasm32-wasip2` installed, linking with `-C linker=rust-lld -C linker-flavor=wasm-ld -C link-arg=--no-entry -C link-arg=--export-memory` (plus `--export=yoake_hook`, `--export=yoake_init`) skips `wasm-component-ld`, so the output is a core module (`\0asm` version 1, checked), with no WASI imports, because the guest is `no_std` + `alloc`. `core` and `alloc` come with the wasip2 target, `rust-lld` ships in the toolchain. Build code: `tests/support/build.rs` (also used by the engine test).

The crate (`no_std`, builds on host and wasm32):
- `call` (256-byte first buffer; if the result did not fit, it takes it by ticket with `engine_take` and **never re-calls**), `original`, `get`, `set`, `report`, `Registrar::hook`, `Handle`, `Error` (handle statuses decoded; `is_stale`), `export_guest!(init, hook)`.
- `wire`: the guest codec, the same bytes as the host's (generated from `codec.rs`; round trip and layout tests).
- `heap`: a size-class free-list allocator over `memory.grow` (wasm32) and a trapping panic handler.
- `stubs::{entities, items, game_items}`: **generated by yoake-bindgen** (`guest_stubs` in `bindgen.json`, the new guest output mode): 279 typed functions (179 entities, 93 items, 7 Game-path handle makers) with the engine's data types as guest structs and enums (`types::Vec3`, ...), the same binding ids and wire bytes as the host glue, write-backs for `&mut` arguments, getters for every data field, setters only for writable fields. `--check` covers them. Skipped (no stub): bindings with a `Game` receiver (a guest reaches `Game` only through path handles) and shapes the guest cannot hold.

**Shadow stack and allocator across re-entry** (a Rust guest, `tests/guests/reentry.rs`, run on the slice runtime): host -> guest hook 1 -> `original` -> engine body -> hooked function -> the same guest, hook 2 -> back. The outer hook keeps a 200-element heap vector, a 64-byte stack array and a recursion 20 levels deep (32-word array per level) alive across `original`; the nested hook allocates (500 elements) and recurses 30 levels. Afterwards the outer's heap, stack array and recursion result are unchanged, it can still allocate, the nested result equals the host's own computation, the nested hook's write through its handle landed, and a second run reuses freed blocks with nothing drifted. A fourth guest test calls bindings through the SDK with a 300-byte result: it arrives whole through the ticket and the binding ran once.

## 4. `yoake2_server_tick` wired, end to end with a real `Game`

- **One call site**: `native_lifecycle_server_tick_start` (`ServerTickStart`, only for a real tick of a running server) calls `self.yoake2_tick_hook()`, which is `Game::yoake2_server_tick` with the feature and an empty inlined function without it (that file may not contain a `cfg`). It dispatches hook `HOOK_SERVER_TICK` with the `Game` as root.
- `yoake2_dispatch` (game path bindings, then entities, then items) and `yoake2_install_dispatch()` are the engine's `engine_call` table.
- **Test with a real `Game`** (`game/yoake2_game_tests.rs`, ignored, needs `HORIZON_TEST_RESOURCES=C:\Users\USER\NestgateHorizon\horizon\.local\horizon-client\26.3`): it builds the SDK and two guests with `rustc`, builds an integrated-server `Game` from the real resources, drops two item entities (ids 4242 and 7) and runs `native_lifecycle_server_tick_start`. Results:
  1. no mod installed: the tick works, nothing changes;
  2. a guest that registered another hook is not entered (`entries == 0`, no reports, item untouched);
  3. the server-tick guest finds item 4242 by id through `Game.dropped` (generated `Game.item_entity#handle`), reads its position (12.5, 64.0), writes `fire_ticks = 55` through the generated setter, and a request for item 1 is `Stale` (not a trap): `fire_ticks == 55` in the `Game`, the other item untouched, mod enabled, no activation or path handle left open;
  4. after the item is removed, the same guest gets `Stale` for it and the game goes on.
  This replaces the mirrored resolver of MX3R1 with the generated resolver on a live `Game`.

One thing the baseline caught: `native_hooks::tests::lifecycle_source_stays_hookable` forbids any `cfg` in `native_lifecycle.rs`, so the first wiring (a `#[cfg]`ed call) failed it (1192 / 1 failed). The call site is now `self.yoake2_tick_hook()` with no `cfg` in that file; the method is defined in `native_client_items.rs` as the server-tick hook with the feature and an empty `#[inline(always)]` function without it. Feature-off behaviour is unchanged (an empty inlined call).

## Open

- Hook ids of S2 slots are not yet mapped to `dispatch_id` calls in the generated shims (the codemod still emits `dispatch`, id 0); the id table is the ledger's job. Only the synthetic server tick uses a distinct id today.
- Priorities are stored and reported, not used to order several mods.
- The guest allocator never returns memory to the host and has no `realloc` in place (a copy); fine for tick-sized work, not measured.
- Stubs for the `Game` receiver functions (`call_game`) do not exist by design; `Game.mobs` / `Game.player` paths still need their modules generated.
- The e2e test builds guests with `rustc` at test time (about 5 s) and needs the game resources, so it stays `#[ignore]`.
- Miri unavailable; the guest-side `unsafe` is the SDK's imports and allocator only, the generated stubs contain none.
