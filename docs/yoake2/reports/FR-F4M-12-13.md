# FR-F4M-12-13: the custom mob debug view and hot reload

Branch `yoake-free/f4m-12-13` (from `yoake-free/merge` 94888c119). Design: `docs/yoake2/FR-F4-MOBS.md`, section 3.11 and
"### F4M-12" / "### F4M-13".

## Implemented against the design

### F4M-12: debug view and commands

| Design item | Done |
| --- | --- |
| `/yoake mobdebug [on\|off] [hitboxes] [bones] [anim] [ai]` | Parsed by `mobs/custom/debug.rs::parse` (nothing toggles, `on` is all four, part names alone switch exactly those on, `off` switches off). The view is per player: it lives in the window's game (`CustomMobDebug`, one byte), nothing is sent. |
| Key chord | F3+M (`DebugAction::MobDebug`, one entry in `HORIZON_ACTIONS` of `debug_keys.rs`, one arm in `game/debug_keys.rs`); only in a world that has custom types. |
| Gizmo drawing | `plan()` turns each mob (nearest 48 within 48 blocks) into shapes that `game/custom_mob_debug.rs` hands to `gizmos.rs` through its public API only (`line`, `cuboid`, `arrow`, and `on_top` lines): hitbox parts as boxes (green hurt+pick, red hurt only, blue pick only, grey switched off), the skeleton as parent-to-child lines in the pose the mob is drawn in, locators (cyan) and seats (orange) as small boxes, the AI target as an arrow, the navigator's path. |
| Overlay text | Billboard text through the name-tag path (as `debug_renderers.rs` does): per mob a header (`type #id hp`), per controller layer its state and clock time, the synced values, the running goals and target goals and the brain's activity; names on the hitbox parts, bones and locators. |
| `/yoake mobs` | Per type live and drawn mobs, the measured client cost per frame (pose and vertex build, in microseconds), then the path-budget lines of `/horizon custommobs stats`. The meter starts with the first call (two clock reads a mob, only while it runs) and `/yoake mobs stop` ends it. |
| Off by default, free when off | `DebugView` is `0`; `custom_mob_debug_gizmos`, `custom_mob_debug_geometry` and `custom_mob_debug_draw` return on their first line (no list, no allocation); the cost meter is a `Cell<bool>` read once per drawn mob. |
| Where the commands answer | In the chat box, on any server: `handle_chat_input` hands `/yoake mobdebug`, `/yoake mobs` and `/yoake mob reload` to the window's own game before the line goes to a server. The command tree (`horizon-command/src/vanilla.rs`, with Horizon's own commands on, game masters) has them too, for completion and the control socket's `command` (that one runs on the server side of an integrated server, where there is no view; the e2e therefore types them with the control socket's `chat`). |

### F4M-13: hot reload

| Design item | Done |
| --- | --- |
| R1 asset watcher | `mobs/custom/reload.rs::Watcher` (one for the process) polls, once a second from the window's game tick, the files of every registered type: the type JSON, geo and bbmodel, animations, controllers, textures and glow masks. A change counts when the files stayed the same for a whole poll. Sources are registered only in developer mode (`YOAKE_WASM_UNSIGNED=1`) for a content folder without a `SIGNATURE` (`game/mods.rs::content_root`: a `--dev-mod` folder or an unsigned installed package). |
| Safe swap at a frame boundary | The new type is read through the same loaders as the first load (`reload::rebuild`), installed in the registry, and every live mob of the type is brought over in the game tick (between two frames): `reload::sync_mobs` (kind, built-in numbers, attributes with their modifiers, hitbox switches by part name, the goal list when `ai` changed), then the render state (`MobRender::rebind`) and the animation stores (`retype` on the local mirror and on a remote client's store). A mob spawned from the old table is brought over within a tick. |
| R2 `/yoake mob reload [type]` | Rebuilds the named type (every reloadable one) now, reports `Reloaded <type> (N mob(s) now use it)` or why not; a changed texture goes through the resource reload (F3+T) because the textures are in the atlas. |
| R3 server module swap | `wasm_mods/full.rs::FullMod::reload_server`: with `YOAKE_WASM_UNSIGNED=1` **and** `YOAKE_WASM_SERVER_RELOAD=1`, an unsigned server module's file is watched (the existing dev `Watch`) and a new build is swapped in under the module lock at the next `server_tick`; the masks are read again and the next world starts from the new bytes. The guest's own memory starts afresh (design risk 11). |
| Failure handling | A file that does not parse or load keeps the old type running and logs one warning that names the file and why (`Horizon custom-mob reload: <type> not reloaded, the old version keeps running ...`); a bad server module build keeps the old instance. A change of the synced values or the animation layers is refused (`compatible`: the wire layout hash differs) with a message asking for a restart. |
| Per-mob animation phase | The phase is carried by the clocks the server anchored, not by the type; `rebind` drops only what the old model shaped, so the next update takes state and clocks from the anchors (the late-join rule). |

## Findings

1. **The control socket's `command` runs on the server side of an integrated server**, not in the window's game; a `/yoake` command typed in the chat (`chat` on the socket) is answered by the window's own game. The first e2e run used `command` for the view and nothing was drawn for that reason. The chat interception is the real player path (and works on a dedicated server too); the command tree entries are for completion and for `command`.
2. **A game keeps two copies of the game state in one process** (the window's game and the integrated server's), so the file watcher is one for the process (`reload::watch_poll`), only the window's game polls it (it alone has the renderer a texture change needs), and each game brings its own mobs to the registry's types in its tick.
3. The game's log file is written in blocks: short runs lose their last lines until enough is logged (found while debugging finding 1).
4. A resource reload (F3+T, or a texture change) rebuilds the registry from the mod folders (`build::add`); now that the live mobs are brought to the registered types, they pick the rebuilt types up too.

## Left open

* **R1 textures** are applied by the resource reload (F3+T), not swapped in place; a changed texture in the e2e was not exercised (only geo and the command).
* **Debug view**: "the transition that fired" of a controller is not shown (the client keeps only the state and the clocks), nor the animation's weight; the server tick cost per type of `/yoake mobs` is only the path-search counters of `/horizon custommobs stats` (there is no per-type server span timer to read); the overlay is not tested for a very large number of bones (labels stop at 48 bones). A remote client's mobs have no goals or path (the server owns them), so `ai` shows the target the synced state allows (none) and the brain activity only on the host.
* **R2 on a dedicated server**: the definitions are read by whoever has the dev folder; a client of a dedicated server reloads its own copy of the type (assets), a server needs its own `/yoake mob reload` (the same command in the server console is not wired: the tree entries exist for the integrated server and the control socket).
* **R3** is tested with the demo server guest only; a custom mob script goal (`fox_ai`) across a swap was not run in a game (the guest's own memory starts afresh by design), and the `--wasm` variant of the render e2e was not run.
* The two commits are split by file: the F4M-12 commit holds the debug view's own files and entry points; the shared glue (the command tree, the chat interception, `game.rs` fields) arrives with the F4M-13 commit, so the first commit alone does not build.
